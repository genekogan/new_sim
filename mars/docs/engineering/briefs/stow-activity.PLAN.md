# Explicit stow / activity preparation feasibility

Read-only source inspection: main `cb5ff57`, `<mars-campus-repo>`. Read AGENTS, ENGINE_GUIDE, SIMULATION_VISION, ACTIVE_ROADMAP and ITEMS. No dirty held-source bridge files accessed or changed; no browser, gate or paid calls.

## Smallest supported action

Propose registered `stow_items {actor, placements:[{item,surfaceSlot}], allowGround?:boolean}` with1–2 placements. Require exact explicit held item IDs, unique item IDs, and coverage of all current small held items; deterministic requested order. Surface IDs come from the caller's authored/approved layout choices. Literal ground requires explicit allowGround=true and at most one ground placement in this initial scope; two ground placements refuse because current put_item would drop both at the same point. Never silently substitute a different destination or drop unwanted food to satisfy an activity.

Start only standing/free on the ground, no access links, no construction grip, no actor/hand/item ownership by an unrelated action. Seated eating/serve must be explicitly ended and safely stood up first; do not build stand/recovery or meal scheduling into this first action. Parent preclaims actor, listed hands/items, and destination surface slots, delegates one ordinary physical put_item child at a time, waits for actual completion, and checks that each item's support records the approved destination. No direct pose/support writes. Keep hold_items independent: it only owns holds:<actor> and continues following any remaining held item until hands are empty.

Readout: preparing/stowing/prepared/stopping/cancelled/failed; current item/destination, completed placements, remaining in-hand items, waiting/refusal. Successful preparation only means hands empty. Work/join remains a subsequent explicit user action. Partial placement is not rolled back on failure/cancel.

## Existing mechanics and prerequisites

1. **Current small-item admission gap.** construction/rules.ts124 holdingDiagnostic only checks human.grip, not support.kind=in-hand. classroom.ts486 initial entry, classroom.ts184 join, and workstation.ts239 use that helper, so a bowl/spoon currently does not prevent class or computer work. Add a separate narrow free-small-hands guard only at those admissions. Do not change holdingDiagnostic globally: take_item uses it and must still allow taking a second item; sit/eat/serve intentionally support held meals.

2. **Parent-child ownership is sufficient for stow itself.** Runtime reservationConflict393–400 excludes ancestors; parent actor/hand/item claims delegate to child put_item and walk_to. hold_items only owns holds:<actor>, so is compatible. Claim both hands (even empty one) if preventing a new take during preparation is required. Claims persist until child stops and parent ends. No Runtime redesign is needed.

3. **Destination claim prerequisite, small but required before general concurrent surface stow.** put_item reservations at items/actions.ts227–230 currently claim actor/hand/item only. A new parent-only surface token would not block existing standalone puts. Destination occupancy is checked before reaching at267–269, then placeOnSlot293 releases after0.4s without rechecking. Two actors can both pass the free-slot check and place into one slot. Add the same exclusive `surface-slot:<owner#slot>` reservation to ordinary put_item and the parent, plus a release-time occupancy recheck if external fixture mutation is supported. This is a bounded put_item edit, not inventory redesign; do not claim concurrency-safe stow before it is done. Fixed authored surfaces may explicitly exclude movement; moving surfaces require stable owner claim or binding revalidation, which is out of first scope.

4. **Ground is narrower than generic item placement.** Ground put computes one point0.55m in front of the standing actor at actions.ts190–205. Sequential two small bowls/spoons can overlap because low items are not navigation obstacles. Initial scope supports only one explicitly permitted ground placement, and must check other grounded item's actual footprint at that point; refuse occupied/blocked ground rather than invent offsets. Author-approved surface slots are the recommended two-item path.

5. **Cancellation preserves support, no set-down choreography prerequisite.** Ordinary put_item cancel306–312 stops light transfers immediately. Before release the item stays in-hand and independent hold_items continues; after release it stays resting-on/ground while the hand withdraw is cancelled. Runtime cleanup546 cancels child descendants. A preparation parent should explicitly cancel/wait for live children before releasing claims (deferred parent stop), preserving already-placed items and listing remaining held items. Scope excludes stairs/access or construction carrying; those have different safe-stop obligations.

6. **Do not nest work/classroom continuation yet.** work_at plan241 rejects any actor holder including a prospective parent; classroom initial/join also have explicit busy admission. Finishing stow then a separate registered request avoids changing existing admission ownership. An atomic stow→work parent would need narrow ancestor-aware admission APIs and reservation handoff; stop/escalate if that becomes mandatory. No auto activity retry after a refusal.

## Decision

Stow parent/child execution and cancellation fit the existing Runtime. Before stow, land the narrow small-item admission correction and the shared destination reservation/recheck prerequisite. No larger Runtime prerequisite is necessary for standalone ground-only preparation. Atomic next-activity chaining, moved surfaces, two arbitrary ground drops and seated meal recovery should be explicit later increments.
