# Mars simulation

Cloudflare Worker endpoint `/mcp` uses the official MCP TypeScript server and its native Streamable HTTP handler. `MarsSimulation` is a SQLite Durable Object per room. Room state persists independently of any browser. The existing site and model downloads stay in the same deployment.

Create a room in the studio and copy its connection configuration. The browser generates a random 256-bit control capability. `view = SHA256(control)` and `room = SHA256(view)` allow the worker to authenticate control and read-only access without storing plaintext credentials. Bearer format is `room.capability`; keys never go into API URLs. Shareable spectator links carry only the view capability in the fragment. Possession grants access to that room, not to Cloudflare or campus files. Leave/create makes a new independent room; it does not revoke old invitations. OAuth and per-person account revocation are not implemented.

## State and commands

Twenty tools (plus the preview `engine_*` tools below) cover discovery, time/day length/simulation rate, weather, static cameras/orbits/spirals/keyframe paths, people/groups/activities, EUC missions, fire, seven gallery screens and atomic scene batches. The full external-agent contract is [public/simulation-agent-guide.md](../public/simulation-agent-guide.md), also published at `/simulation-agent-guide.md`. Schemas live in `commands.ts`; MCP `get_capabilities` returns their JSON Schema plus landmarks/IDs.

The server stores immutable motion paths and an anchored virtual clock `{real, virtual, rate}`. Pause freezes virtual time; rate changes re-anchor it without changing poses. `normalizeState` migrates old room state on read, preserving active and paused timelines. Commands clone before mutation and commit transactionally. `apply_scene` validates up to 12 children and commits one revision or none. The HTTP command endpoint has UUID idempotency keys (last 256 revisions). MCP creates a new command ID per invocation: retries are separate invocations.

Viewers poll once per second while visible, with cancellation, bounded timeout and error backoff. `?revision=N` returns only `{unchanged:true,revision,now}` when unchanged, avoiding repeated route/trajectory transfer and pose computation. A DO instance caches its loaded state and invalidates that cache only after a successful command transaction. No browser telemetry or archive data is sent to the server. Strict bounded schemas, authenticated body limits and same-origin browser validation guard the command surface.

Routes use baseline mesh bounds, inflated for people. Ground-level walking is currently mapped within ±60 m of Chiba; stationary indoor people are not routed through walls/stairs. EUCs follow an outer rounded rectangle enclosing the full model, or obstacle-aware connector routes to six campus parking docks. Return/dismount leaves the rider standing beside the wheel; circle remounts and approaches the perimeter without teleporting. A single campfire is placed in a three-metre-clear clearing; `start_activity` with `campfire` uses that clearing. Activities and generic people are illustrative, separate from the editable replica. Local layout editing is locked while connected. Shared routes do not yet model pedestrian collision avoidance or movable geometry.

`get_state` returns current interpolated poses and room state. New rooms start at 16:00 with the day–night cycle off; the room toggle and `set_environment` can enable passage of time. Existing rooms retain their chosen environment. The camera is a desired broadcast shot, not telemetry from a viewer. Viewers opt into remote camera following; static shots apply once per revision; trajectories are evaluated every frame while Follow remote camera is enabled. Pause and simulation rate affect the trajectory as well. No screenshots or rendering are returned by MCP.

## Engine tools (preview)

`/mcp` also exposes thirteen `engine_*` tools generated from the engine controller's op registry (`../engine/api/schemas.ts`, `controller.ts`) — the same registry, zod schemas and `rehearse`/`execute` code the browser and Node tests use; there is no separate control path. `engine-tools.ts` registers them (listing each op's zod JSON Schema but passing input through, so validation failures come back as the controller's JSON refusal envelope, not SDK plain text); `engine-room.ts` keeps one `EngineController` per room/year inside `MarsSimulation` and persists it in `engine_blobs(key, chunk, data)` (≤ 512 KiB UTF-8 chunks (Unicode code-point boundaries), year-prefixed keys: `history` — the checkpoint/workspace index only, `state/<stateHash>` — one immutable blob per world state, `state/resume.<hash>` — a pause checkpoint's runtime snapshot + run state (`engine_execute pauseAt` / `engine_resume until`; counted with the states), `plan/<hash>`, `take/<id>`, `cams/<takeId>`), loading the index on first use and states/takes/plans/cameras on demand; an old-format `history` blob with inline states is migrated on first load. Each op persists its changes in one transaction; a commit writes only its new state plus the index, and `rehearse` writes nothing unless `keep: true`. Stored plans/takes are capped per room/year (64 plans, 32 takes; creation order in `store-index`): a store past a cap evicts the oldest ones no live workspace's `simulation-run` checkpoint references (a take goes with its `cams/`; `engine_delete_workspace` frees a deleted workspace's runs, `engine_list` shows the ledger); if every stored one is referenced the call is refused with `room.storage-full` and nothing is persisted — delete workspaces or continue in a new room. `GET /api/simulation/engine/take?id=&from=&to=&entities=&include=` returns a compact take slice for viewers (view capability suffices). Rooms seed the synthetic `proving-ground` and `carry-yard` canonical workspaces (with regions and a campfire + benches); year rooms 2020–2026 (`?year=`) also seed protected canonical `mars-<year>` from `public/engine/campus-<year>.json`, bundled into the Worker by `campus-years.ts` (a room seeded earlier gets it on its next load). 2026 uses the existing CAD reconstruction, with its generic context people and no hypothetical flagship inventory; its canonical is protected like the historical years. Existing 2026 rooms gain this canonical once on their next load, preserving their prior workspaces and heads. A legacy editable workspace already named `mars-2026` yields `room.campus-conflict` and is preserved; migrate that work or use a new room rather than overwriting it. Workflow and tool contract: the "Engine tools" section of the agent guide.

Measured in `wrangler dev` (local workerd, M-series laptop): rehearse of the 60 s three-walker plan ≈ 200–260 ms in-DO (≈ 150 ms in Node), execute ≈ 200–270 ms, a 33 s two-person 12 ft beam carry ≈ 230 ms, a 60 s frameGroup camera track ≈ 230–300 ms. Stored: 60 s take ≈ 29 KB, plan ≈ 2.3 KB, history ≈ 5–7 KB after a few runs, camera track ≈ 100 KB (10 Hz samples). Engine code adds ≈ 260 KB (unminified) to the worker bundle. The same plan produced a byte-identical take id in Node and in workerd. These runs are far below DO CPU limits (30 s default), so no chunking of simulation is done. These measurements cover only the small scenes, not arbitrary admitted inputs.

## Room storage and workload admission (LM-018 / LM-019)

Persistence measures UTF-8 bytes (`LENGTH(CAST(data AS BLOB))`), including the stored-byte metadata and plan/take ledger. Every JSON blob is capped at 8 MiB and all blobs of a room/year together at 64 MiB, in addition to the existing plan/take count caps. SQLite rows contain at most 512 KiB, split only between Unicode code points. If a blob or the post-eviction room exceeds its byte cap, `room.storage-bytes` names the key/room and measured limit; the entire operation rolls back, its cached controller is discarded, and `_meta.stored` is empty. Seed migration has the same transactional protection. Existing data remains readable. The room cap includes state history and resume snapshots, not just takes. Byte caps refuse rather than automatically discard referenced history; shorten the take or continue in a new room.

Synchronous room runs currently admit at most **96 steps and 128 entities** in each relevant baseline/current world. `bind_plan`, `rehearse`, `execute` and `resume` enforce this before running; resume includes appended commands. Older saved plans cannot bypass admission. Exceeding either limit returns `room.workload-limit` with counts and workspace/checkpoint subjects and performs no simulation or persistence. The local studio/controller remains unrestricted by these host limits. The runtime's existing 30 simulated-minute tick budget is unchanged.

The real 2022 east-house first-bay chapter currently has 185 steps and 16 entities and is explicitly refused by this policy (SQLite room regression, including migrated old plans). This is a conservative product boundary, **not proof that every smaller workload finishes within 30 seconds of CPU**: navigation/construction cost varies. Larger chapter support requires a measured workerd acceptance case or segmented execution before lifting the limits. Cloudflare documents a default 30-second invocation CPU allowance and 2 MB SQL row limit: [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/). The application limits leave headroom below storage row limits; no CPU configuration was raised.

## Development

- `node deploy/catalog.mjs`: derive geometry obstacles and people from the baseline GLB, with no textures or private provenance copied.
- `wrangler dev --config simulation/wrangler.jsonc --port 8797 --inspector-port 9237`: isolated local DO server. Vite proxies the simulation routes here.
- `node deploy/simulation-integration.mjs`: real MCP handshake/tool calls, auth/isolation/idempotency tests. Set `SIM_BASE` for production verification. Creates disposable isolated rooms and writes test capabilities only to ignored `.cloudflare/simulation-test-room.json`.
- `npm test`: motion, geometry and camera tests.
- `wrangler types --config simulation/wrangler.jsonc simulation/env.d.ts`: regenerate runtime and binding types.
- Release: existing `deploy/prepare.py`, build (which runs `deploy/configure.mjs`), then `wrangler deploy --config dist/server/cloudflare.json`. Configure bundles the MCP worker and exports the DO class with its SQLite migration.

## Historical campuses

The shared studio supports 2020–2026. Use `?year=YYYY` on `/mcp` and every `/api/simulation/*` request. Omission selects 2026 for compatibility. DO identities include year for historical rooms; the existing 2026 namespace is preserved. `get_capabilities` returns the selected year, its entity IDs, bounds and landmarks. Run `node deploy/history-catalog.mjs` whenever historical geometry changes, before building. This generates navigation obstacles and visitors from the actual scene, not a second hand-maintained map. Layout imports reject a different year.
