## Rebuild and create locally

From the worktree, choose an empty scratch output/data directory and a permitted local port. The builder uses a fresh in-memory database and applies every ordered batch through the real Godmode compiler, recording small compiler-suggested collision setbacks (up to 4 m) and aborting on other refusals. It writes the template and an inventory/snapshot into `EDEN_BUILD_OUT`. It does not operate a running world.

```sh
DATA_DIR=/path/to/scratch EDEN_BUILD_OUT=/path/to/scratch node tools/god-skill/scripts/eden-2026/build.mjs
WEB_DIR=/path/to/tested/web/dist node tools/god-skill/dev-world.mjs eden-2026 PORT --data /path/to/fresh-world --genesis worlds/templates/eden-2026.json --fresh
```

Use the tranche heavy-slot wrapper around the builder, and check available disk first. `--fresh` erases only the explicit scratch directory: never point it at an existing world. The release owner creates this world through the launcher; no deployment is performed by this lane.

## What is and is not resident parity

The existing world-engine bridge provides real rooms, doors, stairs, seats, bed posture, carryable items and support surfaces. The existing native ground gives terrain/water to the simulation. Owner time, weather, editing and prayers are shared features. Source support alone is not an executed action receipt on this large template.

| Feature | Content in this template | Remaining parity requirement |
|---|---|---|
| Walk/enter/climb | Native building rooms, entrances, stairs, outdoor regions and paths | Qualify the complete public-route/upper-floor matrix; old indoor IDs are not blindly reused. |
| Sit/rest/sleep | Actual seat and bed slots, thirty commons mats, furnished homes | Old persistent mat ownership and finite needs/sleep policies are separate from bed posture. |
| Read/carry/put down | Books, shelves, tables and carryable kitchen objects | Execute final-world native terminal receipts; old authored shelf approaches are not automatically recreated. |
| Music, painting, computer work | Library furniture/recipes and relevant props | Components do not automatically reproduce the old activity-spot bindings, animations or outcomes. |
| Cooking/eating/fire | Kitchen/dining furniture, pots and fire action | Old finite provisions, delivery/refill and warm-by-fire semantics are not established by decoration. |
| Sports, gym, playground | Courts and playground fixtures | Old volleyball/pétanque/frisbee/gym spots require native bindings and proof. |
| Balloon/transport | Core balloon with basket/envelope and carrier metadata, boats and piers | The old route, boarding and rider retention do not follow from carrier metadata. |
| Lecture/construction | Campus/classroom/workshop architecture | Old lesson delivery, audience roles and construction workflow are not proved by furnishing. |
| Social/account/history | Common new-world systems | No old residents, memories, schedules, account holdings or event history have been converted. |

`worlds/eden/activity-spots.v1.json` declares 95 spots across 20 activity kinds. The generic `main.ts` ledger is not given that file's `spots` option. Its original interior coordinates/native wall IDs also differ from the new entity rooms. Copying this JSON unchanged would not establish working parity. A component/slot-aware binding pass and native action receipts are required before claiming all old resident activities work here. See `apps/server/src/god/engine-bridge.ts`, `packages/engine-mars/src/catalog-adapter.ts` and `apps/server/src/edge/ledger/{ledger,activities}.ts`.
