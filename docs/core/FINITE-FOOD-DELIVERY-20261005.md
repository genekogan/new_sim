# Explicit finite food delivery (T074)

Actual hot-frame evidence showed all eight personal bowls and four kitchen pots
empty. The initial meals and finite preparation worked; they do not sustain
repeated meals indefinitely. This optional source-owned path adds one explicitly
requested batch of eight new prepared meal bowls. It never refills, erases or
renames a consumed bowl/pot, rewrites preparation progress or resets needs.

`commons-food-delivery/1` is a guarded named rules fact containing delivery ID,
sequential batch, eight portions, source tick/rules/state/base and additions hash.
The compatible reader uses a short `+fd/1` rule suffix once, not a growing suffix
per delivery. Existing actor/body/owner/history/kernel/food/rest remain. Each new
bowl uses the existing native bowl def, ground support and hypothetical explicit
prepared stew fraction1. Its home is offset from old personal bowls/spoons; no
existing item is moved. Exact native snapshot is required and a detached graph
checks retained bodies/physics before acceptance. Header/fact commit atomically;
committed fold failure replays exact history. Station carry stays refused.

Batches1–4 are bounded lifetime provisioning slots, eight portions each. Duplicate
ID, fifth batch, identity collision, incompatible reader/state or non-resumable
boundary refuses. No automatic day/routine restock, unlimited source, operator
spend/economy rule or promised perpetual food. Later provisioning requires another
explicit finite request/new approved source path; exhaustion remains visible.

The first eight lifetime birth slots receive actual owned `eat delivered meal`
and tidy cards using their existing spoon. Current owner/body/mind/retirement is
rechecked at card acceptance. Native take/eat/put remains authoritative. Busy
hands/held old empty bowl must be tidied normally; no hand clearing or teleport.
New food is available to ordinary owner requests and eligible autonomous choices.
A passive readiness hook keeps HTTP/clock/ordinary activity running, installs
once at a safe boundary and follows later canonical births without new stock.

Local entry optional `foodDeliveryId` / `PREVIEW_FINITE_FOOD_DELIVERY_ID` selects
the compatible retained reader before boot; body/mind/model configuration stays.
The same ID on restart is idempotent. Keep this reader after a +fd/1 header even
when a request flag is removed. Public `scene.foodDeliveries` publishes finite
batch IDs/index, portions, bowl/spoon/home/index resources, never private Soul
owners/intentions. Existing provisions/kitchen/shore metadata remains. Kitchen
hooks recognize their policy when later additive suffixes exist.

Fake-$0 proof: eight invited human owners retain bodies/regions/canonical prefix,
each gets a full new bowl and card. An owner eats its initial meal and later
consumes a new delivered meal; old empty bowl stays empty, seven other new bowls
stay full. Native/kernel/needs snapshot and genesis replay agree. Delivery after
accepted shore preserves old resources and actual body pose, starts no activity,
retains shore rendering, restores exact snapshot and enforces duplicate/cap.

slash while delivery IDs use narrower characters; campus schema corrected to
