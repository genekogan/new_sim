# Thirty arrivals through the normal owner API

The earlier thirty-owner keeper proof began with pre-adopted canonical owners.
This proof begins with zero Souls in a fresh isolated SQLite world containing the
same recorded physical/core/life/finite-resource/sleep checkpoints. The actual
normal main.ts process creates all thirty owners through its existing HTTP path.

For each distinct synthetic human identity, an administrator issues a one-use
invite, the owner redeems it and submits the existing lifecycle-opted creation.
Its private receipt reaches admitted and native body readiness. The owner's me
response includes that exact Soul; another identity receives 404 for the receipt.
All thirty identities and body IDs are distinct. Every owner gets the exact finite
meal binding for its canonical arrival slot; cross-owner capabilities are denied.
No legacy direct create bypass is used for these arrivals.

Owner thirty submits ordinary rest, receives its understood receipt and actual
native rest presentation, and reads strict own private purpose context with
no-store. Only the synthetic administrator can pause. Actual SIGTERM saves the
ongoing native rest interval. The database contains thirty complete lifecycle
operations and matching canonical births. Restarting normal main on the same DB
preserves those exact operations, all owner rows, old canonical event prefix,
finite resource header and own purpose/recall. Paid cost remains zero.

The final source run passed in 14.12 seconds. Invite issuance through native-ready
receipt took 177–257 ms per sequential synthetic admission in that run, including
local HTTP/polling overhead. This is a diagnostic observation, not first-motion
latency, a concurrent-load benchmark or a real-provider/SSO promise. The prior
sampled-binding run passed before the final all-thirty-binding and lifecycle-record
assertions were added. Types pass. Sanitized child environment uses fake minds,
zero budget, dev authentication, no provider/archive credentials, loopback 4955;
own children/listener and temporary data close after each run.

The full30 World-approved layout is a finite recorded checkpoint in a fresh
fixture. No live world is expanded or reconfigured by this test. No finite meal is
refilled or recycled. Thirty native arrivals and bound resources do not prove all
thirty activities, sustained food supply, real humans, agent hosts, browser/device
experience, concurrent capacity, FPS or combined release readiness. Normal create
remains its existing one steering/ownership mechanism and allocation policy.
PM owns coordinated integration and release after Gene's held handover.
